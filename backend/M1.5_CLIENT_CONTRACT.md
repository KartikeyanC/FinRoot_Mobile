# M1.5 — client contract (for M5, the sync engine)

How the Flutter app will call `apply_transaction_mutation`. **Not wired yet** —
this is the reference M5 builds against. No transaction feature exists before M7.

---

## The call

```dart
final res = await supabase.rpc<Map<String, dynamic>>(
  'apply_transaction_mutation',
  params: {'p_mutation': envelope},
);
// res == { status: 'applied'|'replayed', operation: ..., transaction: {...}|null, deleted: bool }
```

## The envelope

```jsonc
{
  "mutation_id":    "<uuid v4>",          // generated once, stored in the outbox row, reused on every retry
  "operation":      "create_transaction", // | "update_transaction" | "delete_transaction"
  "tenant_id":      "<currentTenantId>",  // from currentTenantIdProvider (M3)
  "transaction_id": "<uuid v4>",          // ALWAYS send it. create: the client-generated id that IS
                                          //   the local row's PK (local == server id, no re-keying).
                                          //   update/delete: that same id.
  "payload": {                            // create/update only; omit for delete
    "type":                   "expense",  // income | expense | transfer
    "amount":                 "18600.00", // Money.toStorageString() — string, numeric(14,2)
    "currency":               "INR",
    "category":               "Labour",
    "description":            "Labour salary",   // or null
    "occurred_at":            "2026-09-08T10:30:00.000Z",
    "account_id":             "<uuid>",          // or null
    "payment_mode":           "UPI",             // or null; null for transfers
    "transfer_to_account_id": null,              // required iff type == transfer
    "tracker_id":             null               // optional; never affects a balance
  }
}
```

## Rules the sync engine must follow

1. **One `mutation_id` per logical mutation, forever.** Generate it when the
   user hits Save, persist it on the outbox row, send the *same* id on every
   retry. This is what makes a lost-response retry safe.
   1b. **Generate the `transaction_id` client-side too**, once, at create time —
   it is the local row's primary key and the server inserts with it, so the two
   never diverge and there is no re-keying step.
2. **`update_transaction` sends the whole row**, not a diff — the client holds
   the full local copy. Last-write-wins on the server.
3. **On `status: "replayed"`** — the first attempt had actually succeeded.
   Treat it exactly like `applied`: reconcile the returned `transaction` into
   the local cache, mark the outbox row `synced`.
4. **On a `deleted` create replay** (`transaction: null`, an old create whose
   row was later deleted) — drop the local row; do not resurrect it.
5. **Error handling** (maps to the M2 `Failure` hierarchy):
   | Server error | `Failure` | Retry? |
   |---|---|---|
   | `42501` "Not authorized" | `PermissionFailure` | no — surface it |
   | `22023` bad envelope / reused id | `ValidationFailure` | no — bug, log it |
   | `23503` id not in workspace, `23514` check | `ValidationFailure` | no |
   | `P0002` no such transaction | `ValidationFailure` (update/delete of a gone row — reconcile local) | no |
   | function missing (`PGRST202`) | `UnexpectedFailure` | **hold in queue** — migration not applied yet |
   | network / timeout / `PGRST301` | `NetworkFailure` / `AuthFailure` | **yes**, with backoff |
6. **Idempotency also protects update/delete** — a replayed update returns the
   current row; a replayed delete returns `deleted: true`. Safe to resend.

## What the RPC does NOT cover (still direct PostgREST, RLS-gated)

- Reads (transaction lists, detail) — plain `.from('transactions').select()`
  scoped by `tenant_id`, same as the web.
- Assigning/removing a tracker on existing rows — the web's
  `useAssignToTracker` pattern (`.is('tracker_id', null)` idempotency guard) is
  already replay-safe; M9 mirrors it.
- Accounts, trackers, budgets, goals writes — their own paths (M8–M10).

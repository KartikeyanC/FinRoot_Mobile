---

## 1. One-paragraph summary

The migration adds **one new table** (`client_mutations`) and **one new
function** (`apply_transaction_mutation(jsonb)`). It changes **nothing that
already exists** — no column, constraint, policy, trigger, index, function,
grant, or row is altered or dropped. The web app never calls the new function
and never reads the new table. The only web-repo change required is a **one-line
addition to `src/lib/dataExport.ts`** after regenerating `types.ts` (§4), which
is the same forced-decision the trackers migration triggered.

**Verdict: strictly additive. No web behaviour change. No data change.**

## 2. Exactly what the migration creates

| Object | Kind | Notes |
|---|---|---|
| `public.client_mutations` | table | idempotency-key ledger: `mutation_id` (PK), `tenant_id`, `user_id`, `operation`, `entity`, `entity_id`, `created_at`. **Ids and timestamps only — no amount, category or description.** Same "carries no identity" shape as `processed_webhooks`. |
| `client_mutations_tenant_created_idx` | index | on `(tenant_id, created_at desc)` — housekeeping reads |
| `cm_select` | RLS policy | members read their own workspace's rows; **no** insert/update/delete policy |
| grants on `client_mutations` | grant | `authenticated` → SELECT only; `service_role` → ALL; `anon` → nothing |
| `public.apply_transaction_mutation(jsonb)` | function | `SECURITY DEFINER`, `EXECUTE` to `authenticated` only |

Total: ~1 table, 1 index, 1 policy, 1 function, a handful of grants. No `ALTER`
of anything pre-existing. No `DROP` of anything.

## 3. Why each "could this break the web?" question is *no*

| Concern | Answer |
|---|---|
| **Does it touch `transactions`?** | No. No `ALTER TABLE transactions` anywhere. No column, no constraint, no index, no policy, no trigger. |
| **Does it change RLS?** | No existing policy is dropped or replaced. `client_mutations` gets its own new policy. `is_tenant_member` / `has_menu` / `get_effective_menus` are unchanged. |
| **Does it change how the web writes a transaction?** | No. `src/hooks/useTransactions.ts` keeps its raw `.from('transactions').insert(...)`. The new RPC is a *parallel* path used only by the mobile app. Both write to the same table, the same way, subject to the same CHECK constraints. |
| **Does the new RPC bypass any protection the web relies on?** | No — it re-implements the gate. `SECURITY DEFINER` bypasses RLS, so the function restates `is_tenant_member(tenant_id, 'admin')` explicitly — identical to how `goal_contribute()`, `budget_set_allocation()` and `mark_recurring_generated()` already do it. It is in fact **stricter** than the raw insert: it verifies `account_id` / `transfer_to_account_id` / `tracker_id` belong to the calling workspace (the raw insert does not). |
| **Can it create a malformed transaction the web then chokes on?** | No. It inserts through the same table, so `transactions_type_check`, `transactions_transfer_dest_check`, `transactions_import_hash_key` and `transactions_recurring_period_unique` all still fire. It never sets `source_recurring_id` or `import_hash`. |
| **Does it change grants on existing tables?** | No. The `REVOKE`/`GRANT` lines target only `public.client_mutations` and the new function. |
| **Retention / storage growth?** | `client_mutations` is ~120 bytes/row, one row per mobile write. The table comment states it is safe to prune > 90 days. No pruning is wired in this migration (keeping it minimal); an optional follow-up can add a `retention_policy` key + a line to `prune_expired_data()`. |
| **`ALTER DEFAULT PRIVILEGES` side effects?** | None used. |
| **Does `supabase db push` re-order or conflict with pending web migrations?** | Timestamp `20260909120000` sorts *after* the current latest (`20260908120000_bug001_..._v2`). It is independent of every existing migration. |

## 4. The one required web-repo change

After the migration is applied and `types.ts` is regenerated:

```bash
# from the web repo root, with SUPABASE_ACCESS_TOKEN set.
# Use Bash redirect, NOT PowerShell Out-File (BOM/CRLF — see web CLAUDE.md).
supabase gen types typescript --project-id ludbntvhagefadfkhrjj > src/integrations/supabase/types.ts
```

`types.ts` gains `client_mutations` under `Tables` and `apply_transaction_mutation`
under `Functions`. Both are purely additive to the type — no existing web code
gets a type error.

**`src/lib/dataExport.test.ts` will then fail** ("New table(s) with no export
decision: client_mutations"). It reads the generated types and forces every new
table to be classified. Fix — add one line to `src/lib/dataExport.ts`:

```ts
export const NOT_PERSONAL: Record<string, string> = {
  // ...existing entries...
  client_mutations:
    "Internal ledger that de-duplicates the mobile app's offline writes. " +
    "Ids and timestamps only — the transaction data itself is exported via " +
    "the transactions table.",
};
```

That is the entire web-repo change. (The trackers migration required the exact
same kind of one-line follow-up, adding `trackers` to `EXPORT_TABLES`.)

**Run the full web test suite after regenerating** (`npm test`). Expected: green
once the `dataExport.ts` line is added. No other test reads the schema this way
(`analytics.test.ts` checks for tracking scripts; `menuUpsell.test.ts` and
`menuContract.test.ts` check the menu id list, which is untouched).

## 5. How to apply (suggested)

1. **Review this document + the SQL.** Confirm the "additive only" claim by
   reading the migration — every statement is `CREATE`, `GRANT`, `REVOKE` (on
   the two new objects), `COMMENT`, or an `ASSERT` self-check.
2. Copy `20260909120000_m1_5_client_mutation_ledger.sql` into the web repo's
   `supabase/migrations/`.
3. Apply — either:
   - `supabase db push` (preferred: keeps migration history in step), or
   - paste into the SQL Editor **and** commit the file so history matches
     (the web CLAUDE.md notes the Management API's write path has been blocked
     for some sessions; the SQL Editor always works).
4. Run the **post-apply verification** block at the bottom of the SQL as a real
   signed-in workspace admin over PostgREST.
5. Regenerate `types.ts` (§4), add the `dataExport.ts` line, run `npm test`,
   commit.
6. **Sanity-check the web app**: sign in, add / edit / delete a transaction the
   normal way. It must behave exactly as before (it never touches the new
   objects).

## 6. Rollback

Fully reversible — nothing it created is referenced by anything else:

```sql
DROP FUNCTION IF EXISTS public.apply_transaction_mutation(jsonb);
DROP TABLE IF EXISTS public.client_mutations;   -- CASCADE not needed; nothing FKs to it
```

Then revert the `types.ts` regen and the `dataExport.ts` line. No data loss —
`client_mutations` holds only mobile-sync bookkeeping; the transactions
themselves live in `transactions` and are untouched.

The mobile app degrades gracefully if the function is absent: the sync layer
(M5) detects a missing-function error and holds mutations in the local queue
rather than losing them.

## 7. What is explicitly out of scope for M1.5

- No pruning/retention automation (noted as optional follow-up).
- No equivalent RPC for accounts / trackers / budgets / goals — if their mobile
  write paths later need idempotency it is a separate migration of the same
  shape.
- No web-side use of the new RPC. The web keeps its raw insert.
- The mobile client code that calls this RPC lands in **M5 (sync engine)** — see
  `backend/M1.5_CLIENT_CONTRACT.md` for the envelope it will send.
